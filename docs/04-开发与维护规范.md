# 开发与维护规范

本文件是项目长期维护的「工作纪律」，也是与 AI 协作（如 Codex）时的交接基准：新会话先读本文档与需求/设计文档，再开始工作。

## 1. 工作范式：文档驱动

1. **先写设计文档**：每个新需求在 `docs/` 下写设计文档，复述对需求的理解并列出待确认点；**确认后才动手**。
2. **再写实施计划**：拆任务，每个任务包含文件清单、TDD 步骤、验证命令、提交信息。
3. **逐任务实施**：先写失败测试 → 实现 → 通过 → `npx tsc --noEmit` → 提交一次（英文短消息）。
4. **端到端验证**：全部完成后跑 `node scripts/e2e.mjs`，再用 `node scripts/cleanup-e2e.js` 清理测试数据。
5. **全量检查**：`npm test`、`npm run build`、e2e。

## 2. 编码与验证纪律

- 库存、结算等核心逻辑**只允许经过 `src/services/` 唯一入口**，禁止在页面或 API 里直接改库存。
- 提交信息：`feat:` / `fix:` / `test:` / `docs:` / `chore:` 前缀 + 英文短描述。
- 开发构建与生产构建隔离：日常构建用 `$env:NEXT_DIST_DIR=".next-build"; npm run build`，避免覆盖生产缓存。

## 3. 数据安全规范（重要）

- 改 schema 前先备份：`npm run backup`；标准入口是 `npm run migrate:dev -- --name <描述>`（自动备份 + 生成迁移文件）。
- 迁移文件必须入库，可追溯；破坏性变更（删列/改关系）先写数据迁移再删旧字段。
- 测试数据必须带可识别前缀（如 `E2E`），测试后走专用清理脚本；**含真实数据的库严禁全库 reset**。
- 数据库启用 WAL 模式（`node scripts/enable-wal.js`），备份保留最近 30 份。

## 4. 与 AI 协作的规范

用 AI 助手（Codex 等）维护本项目时，遵循同一套纪律：

1. 新对话先读 `docs/README.md` 与本规范、相关设计文档，不凭记忆动手。
2. 每个需求先交设计文档，列出待确认问题，**用户确认后才写实施计划、才改代码**。
3. 一次只做一个任务，做完跑类型检查与相关测试，成功后才继续。
4. 涉及数据库结构变更必须走迁移流程并先备份；测试只动测试数据。
5. 全量验收（单测 + 构建 + e2e）通过后，用英文短消息提交。
