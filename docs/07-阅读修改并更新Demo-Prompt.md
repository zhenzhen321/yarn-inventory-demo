# 阅读最新修改并更新 Demo：可复制 Prompt

下面这段 Prompt 用于把私有项目中的最新设计、代码和文档修改同步到公开 Demo。它要求先理解改动，再更新演示项目，并在提交前完成脱敏与全量验证。

## 使用方法

1. 把 `<私有源项目绝对路径>`、`<公开 Demo 绝对路径>` 替换成本机对应目录。
2. 把“本次重点修改”替换成当前要同步的内容；不知道具体文件时可以保留默认表述。
3. 将下方完整 Prompt 复制给 Codex 等编码助手。
4. 第一阶段只审阅分析；确认其同步方案后，再让它继续实施、测试和推送。

## 完整 Prompt

```text
你是负责维护「纱线进销存」公开演示项目的资深全栈工程师。请阅读私有源项目的最新修改，将适合公开展示的功能、文档和测试同步到 Demo，并保持 Demo 可独立安装、测试、部署和演示。

项目位置：
- 私有源项目（只作为读取和对照来源）：<私有源项目绝对路径>
- 公开 Demo（唯一允许修改和提交的仓库）：<公开 Demo 绝对路径>
- 公开仓库：https://github.com/zhenzhen321/yarn-inventory-demo
- 目标分支：main

本次重点修改：
<在这里填写，例如：按内部批次记录库存、上下游溯源、二维码标签和扫码出库；如果留空，请根据源项目最新文档和 Git 差异自行识别。>

第一阶段：阅读与分析（先完成本阶段，不要修改文件）
1. 先检查两个目录的 Git 状态、当前分支和最近提交。任何已有未提交改动都视为用户资产，不得覆盖、回退或清理。
2. 完整阅读 Demo 的：
   - docs/README.md
   - docs/04-开发与维护规范.md
   - docs/01-需求分析/需求与目标.md
   - 与本次功能相关的设计、实施、测试和部署文档
3. 再阅读私有源项目中最新或本次指定的需求、设计、操作说明、迁移文件、实现代码和测试。不要只看文件名或 Git 摘要；相关文档必须读完。
4. 对比源项目和 Demo，输出一份同步清单，至少包含：
   - 新增或变化的业务规则
   - 数据模型和迁移变化
   - 服务层、API、页面和交互变化
   - 演示数据、操作说明、测试、Docker/部署变化
   - 不应进入公开 Demo 的内容
   - 准备修改、新增或保留不动的文件
5. 明确所有待确认问题，并给出实施与验收计划。完成后停止，不要修改文件，等待我确认同步清单并明确要求继续。

第二阶段：实施同步
1. 只修改 `<公开 Demo 绝对路径>`，不修改私有源项目。
2. 以业务规则为依据同步功能，不要机械覆盖整个目录。保留 Demo 自身的公开部署能力、/api/health 健康检查、ExcelJS 导出方案以及已有脱敏设计，除非新需求明确要求改变。
3. 数据库结构变更必须提供可追溯的 Prisma migration；库存、批次、销售分配、加工和冲销等核心写入只能经过 src/services/ 中的服务入口。
4. 更新公开演示数据，使新功能开箱即可观察和操作。至少准备能覆盖主要规则的样例，同时保证重复执行 seed 不会产生随机脏数据或破坏数据库。
5. 更新 README 和 docs：写清功能价值、操作入口、完整演示步骤、无扫码枪时的替代操作、限制条件、测试方法和部署方法。文档必须与实际界面一致。
6. 为新增或修改的规则补充测试。优先复用已有测试结构；不得通过删除断言、跳过测试或放宽关键规则来获得通过。
7. 保持 Client/Server Component 边界安全：Prisma Decimal、Date、BigInt 或模型实例传给 Client Component 前必须序列化为普通 JSON 值。

公开仓库安全要求：
- 不得复制真实姓名、手机号、客户、供应商、商品、批号、金额、账号、密码、数据库或业务数据。
- 不得提交 .env、数据库文件、备份、日志、构建缓存、访问令牌、Cookie、私钥或本机绝对路径。
- Demo 登录身份统一使用 admin / clerk 等虚构名称；密码只能来自环境变量或明确标注的本地演示默认值。
- 二维码只能包含随机、不可猜测的扫描令牌，不包含成本、客户信息或其他敏感字段。
- 推送前对已跟踪文件做敏感词、密钥模式、大文件和忽略规则检查；发现疑似信息时停止推送并报告。

验收要求：
1. Prisma schema validate 和 generate 通过；迁移能在全新空数据库执行。
2. npm test 全部通过，并报告测试文件数和测试数。
3. npm run typecheck 与 npm run build 通过。
4. 使用隔离的临时数据库运行完整 HTTP e2e，至少覆盖登录、采购建批、批次库存、二维码/批次码销售、调拨、加工、追溯、结算、冲销、导出和删除保护；结束后安全清理临时数据，不触碰真实数据库。
5. 使用 Docker 从全新数据卷启动，确认 /api/health 返回成功，并验证数据持久化配置。
6. 核对 git diff 和 git status，确认没有意外文件、真实数据或对私有源项目的修改。

提交与上传：
- 只有全部验收通过后才提交。
- 使用简短英文 Conventional Commit，例如：feat: sync latest traceability demo updates。
- 推送到公开仓库 main，并等待 GitHub Actions 完成。
- 若 CI 失败，读取日志、修复、重新验证并再次推送；不要把“已触发 CI”当成“CI 已通过”。

最终回复请简洁报告：
- 已同步的业务能力
- 重要文档和代码位置
- 数据脱敏检查结果
- 本地测试、e2e、Docker 和 GitHub Actions 的实际结果
- commit hash 与公开仓库链接
- 任何未完成项、风险或需要人工确认的决定

如果某一步因权限、网络、缺少文档或环境问题无法完成，请明确说明阻塞点和已经取得的证据，不要猜测成功，也不要擅自扩大操作范围。
```

## 只做审阅、不实施时

如果只想让助手先阅读并提出同步方案，可在完整 Prompt 最后一行追加：

```text
本轮仅执行“第一阶段：阅读与分析”，不得修改文件、安装依赖、提交或推送；等我确认同步清单后再继续。
```
